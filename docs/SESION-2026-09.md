## 1. Por dónde empezar al retomar

El proyecto está **parado en un punto limpio**: nada a medias, nada sin
commitear, todo empujado a `origin/main` (`f16b0e2`).

```bash
git clone https://github.com/JuniorSoft363/gym-one.git
cd gym-one
cp docker/env.example .env
docker compose up -d
```

**Siguiente tarea, ya decidida:** paginar `/admin/log/`. Es el techo real de
escala — con 55.000 registros genera 11,3 MB de HTML porque trae todo el
historial y lo filtra en JavaScript. El comentario del propio código lo admite:
*"Fetch all logs for JavaScript filtering"*. Está en `admin/log/index.php:82`,
la consulta no lleva `LIMIT`. Hay un patrón de paginación ya resuelto en
`admin/users/index.php` (líneas ~90-125) que se puede copiar.

Después, en orden: timeout o caché en la comprobación de versión, e índices en
las columnas `userid`. La lista completa está en `HANDOFF.md` §9.

## 2. Qué se hizo, en orden

1. **Clonar y analizar** el repositorio original. Se documentó la arquitectura y
   se detectaron los problemas de seguridad leyendo el código.
2. **Montar un entorno que funcionase.** No existía: no había PHP operativo, ni
   servidor MySQL, y el XAMPP de la máquina estaba medio desinstalado. Además el
   repositorio **no era instalable tal cual** (ver §4).
3. **Corregir la seguridad**, verificando cada arreglo con ataques reales.
4. **Medir la escala** empíricamente, con 10.005 socios y 55.000 registros de log.
5. **Mover el proyecto** a un repositorio propio con historia legible.
6. **Documentar** para poder retomarlo en otro entorno.

Total: **60 ficheros, 1.527 líneas añadidas, 1.701 eliminadas.** El código quedó
más corto que al empezar, porque se eliminó `admin/dashboard_OLD/` (1.528 líneas
de copia muerta).

## 3. Decisiones tomadas, y por qué

Estas son las que conviene **no revertir sin leer el motivo**.

**Docker en vez de arreglar XAMPP.** El XAMPP instalado estaba roto (carpetas
vacías y un servicio huérfano apuntando a binarios inexistentes). Docker no toca
el sistema, se borra con un comando y da phpMyAdmin y captura de correo de
regalo. PHP 8.2 y no 8.5 (la versión local) porque mPDF y Swiftmailer son
antiguos.

**El campo CSRF se inyecta automáticamente, no a mano.** Hay ~40 formularios en
33 ficheros. Pegar el campo oculto en cada uno es justo el parche que falla,
porque basta olvidar uno. `_csrf.php` reescribe la salida HTML desde un único
punto con `ob_start`. Es un mecanismo implícito y hay que saberlo: si alguna
página llega a generar una descarga binaria directamente al navegador, habría
que excluirla — el filtro ya respeta el `Content-Type`, así que solo afectaría a
una respuesta que no declare el suyo.

**Un helper compartido en vez de copiar el bloque 11 veces.** El proyecto ya
sufre de copia-pega (4 variantes de `read_env_file()`); `admin/_guard.php` evita
empeorarlo.

**La comprobación de rol va antes del handler POST.** En `mainsettings`, `smtp` y
`chroom` el POST se procesaba **antes** de leer `$is_boss`, así que poner la
guarda en su sitio "natural" no habría impedido nada. Si mueves esas líneas
hacia abajo, reabres el agujero.

**`users.userid` ampliado a `bigint`.** Era `int(10) unsigned` (máx. 4.294.967.295)
pero el registro genera ids de hasta 10 dígitos. No es teórico: durante las
pruebas salió el id `9570216276`, que habría fallado.

**Merge en vez de `git push --force`** al mover el proyecto. El repositorio de
destino no estaba vacío: tenía un `Initial commit` con un `README.md`
autogenerado. Se unieron ambas historias para conservar ese commit. El conflicto
de `README.md` se resolvió a favor del README real del proyecto.

**El `.env` no lleva comentarios importantes.** El panel de ajustes lo regenera y
los pierde. Lo explicativo va en `docker/env.example` y en `docker/README.md`.

**Dos documentos y no uno.** `CLAUDE.md` lo carga Claude Code solo, pero asume
acceso al repositorio. `HANDOFF.md` es autocontenido para asistentes que no ven
el código. Si cambias algo estructural, actualiza **los dos**.

## 4. Por qué el repositorio original no arrancaba

Cinco bloqueos, ninguno documentado por el autor:

1. `assets/SQL/Init.sql` **no crea ningún usuario administrador** y no hay forma
   de crearlo desde la interfaz. Era imposible entrar al panel.
2. Faltan la tabla `opening_hours_exceptions`, la columna `logs.details` y la
   tabla `shop_gateway`, todas usadas por el código → error fatal en la portada.
3. `users.userid` desbordaba (ver §3).
4. `login/index.php` llamaba `session_start()` dos veces; el aviso de PHP se
   imprimía antes del `header("Location:")` y rompía la redirección.
5. `register/confirm.php` exigía sesión de socio, imposible para quien acaba de
   registrarse porque el login rechaza a los no confirmados: **el enlace del
   correo de bienvenida nunca funcionaba**.

Más tres directorios en los que el código escribe pero que están en
`.gitignore`, así que no existen tras clonar.

## 5. Lo que apareció al probar, no al leer

Esto justifica el método de trabajo de §7. Ninguno de estos se veía leyendo:

- **`$is_this_boss = isset($_POST["is_boss"])`** comprueba *presencia*, no valor.
  Enviar `is_boss=0` creaba un jefe. Se descubrió al crear una empleada sin
  permisos y ver que salía como jefa.
- **El panel corrompía el `.env`**: el parser antiguo no salta comentarios, así
  que un comentario que contuviera un `=` se leía como clave y se reescribía,
  acumulando basura en cada guardado.
- **Los 748 ms de la llamada a `api.gymoneglobal.com`**, que son el 87 % del
  tiempo de respuesta del panel. Solo se vio midiendo y bloqueando el dominio.
- **El flujo de confirmación de registro estaba roto de raíz** (§4.5). Solo
  funcionaba porque las pruebas iniciales tenían `AUTOACCEPT=TRUE`.
- **`/admin/users/` sí pagina.** En una primera lectura se anotó como
  `SELECT * FROM users` sin `LIMIT`; el `LIMIT` se añade más abajo en el fichero.
  Corregido tras comprobarlo.

## 7. Cómo se trabajó (recomendado seguir igual)

**Verificar contra la instancia en marcha, no leyendo.** Varios fallos de §5 eran
invisibles en el código. Para cada cambio: `curl` contra `localhost:8080` con
cookie de sesión, y consulta a la base de datos para comprobar el efecto real.

**Medir antes de afirmar.** Las cifras de escala salen de cargar 10.005 socios y
55.000 logs, no de estimar. Eso cambió la conclusión: el cuello de botella no era
la base de datos sino una llamada HTTP externa.

**Intentar el ataque, no solo revisar el parche.** Cada arreglo de seguridad se
comprobó reproduciendo el ataque antes y después.

Comandos útiles en `HANDOFF.md` §10.

1. **Credenciales de la demo en ficheros públicos.** `CLAUDE.md`, `HANDOFF.md`,

   `admin/trainers/timetable/index copy.php` y
   `admin/shop/gateway/PAYPALCHECK.php` (demo con email hardcodeado y un

   Composer aligeraría el repositorio, pero rompe el auto-updater del panel, que
   descarga y descomprime el zip del repositorio entero.
